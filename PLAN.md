# План разработки RAG по истории TLS

**Цель сдачи** — из 20 англоязычных RFC получить проверяемый ответ на русском. Читатель видит версию протокола, применимое правило и точные английские цитаты с номерами RFC и разделов. Если документов недостаточно для вывода, система объясняет, какого основания не хватает.

**Рабочая оценка** — 21–28 часов сосредоточенной работы одного разработчика. Семь дней дают время на ручную проверку и защиту. Это оценка при условии, что на Mac с 8 ГБ удаётся запустить локальный генератор с коротким контекстом. День 1 отсчитывается от начала работы, календарный дедлайн уточняется по письму с заданием.

## Что уже есть

- В `data/raw/` лежат полные исходные тексты 20 ранее выбранных RFC, всего 1 940 715 байт. В `data/manifest.json` для каждого указаны месяц публикации, официальный URL, длина и SHA-256. Срез получен 17 ноября 2026 года. Оригиналы нужны в том числе для восстановления дословных цитат. [Условия использования RFC](https://www.rfc-editor.org/series/rfc-use/)
- В `data/dev.jsonl` есть 5 пробных вопросов с эталонными ответами. У отвечаемых вопросов доказательства заданы диапазонами байтов `[start_byte, end_byte)` исходного TXT в UTF-8. Во внешнем массиве перечислены допустимые наборы, внутри одного набора нужны все его фрагменты. Эти примеры доступны при разработке. Финальные 20 подготавливаются отдельно.
- Пробный вопрос про билеты требует сравнить значение нуля в двух конкретных публикациях. В старой это неопределённый срок, в новой — указание сразу отбросить билет. Вопрос о сборке Safari, отключившей TLS 1.0, проверяет отказ. [RFC 5077, §3.3](https://datatracker.ietf.org/doc/html/rfc5077#section-3.3) · [RFC 8446, §4.6.1](https://datatracker.ietf.org/doc/html/rfc8446#section-4.6.1)
- На момент начала работы установлен Python 3.13, архитектура arm64. Команда `ollama` не найдена в PATH. Индекс, запуск моделей и оценка качества ещё впереди.

## Прототип и порядок экспериментов

1. **Подготовить текст один раз для всех методов.** Разбить RFC по разделам и абзацам, сохранить таблицы вместе с заголовками. Начать с фрагментов по 200–300 токенов E5. Проверять длину токенизатором. Исключить из поиска повторяющиеся колонтитулы и оглавления, сохранить связь каждого предложения с байтами оригинала. Показывать извлечённую из оригинала цитату и сверять её диапазон.
2. **A — простой dense RAG.** Кодировать русский вопрос и английские фрагменты через `intfloat/multilingual-e5-small` с соответствующими префиксами. Нормализовать векторы и использовать точный поиск по косинусной близости в NumPy. Для такого корпуса отдельный сервис поиска избыточен. [Карточка E5](https://huggingface.co/intfloat/multilingual-e5-small)
3. **B — добавить BM25.** Объединить ранги E5 и BM25 методом RRF. В этой конфигурации BM25 получает исходный вопрос. Проверяем вклад буквальных совпадений в номерах RFC, версиях и названиях расширений. Разметить, где в вопросе таких подсказок нет.
4. **C — добавить перевод только для BM25.** Один раз перевести вопрос на английский локальной Qwen, сохранить результат, сохранить исходные идентификаторы. Dense-поиск продолжает работать по русскому запросу. Сравнение B и C показывает эффект перевода. Практическая гипотеза — он поможет на вопросах без английских терминов, но может потерять отрицание или условие.
5. **D — при наличии времени учесть дату.** Добавить к C только ограничение даты публикации для явно исторического запроса «что было известно на дату X». Для вопроса о сравнении двух редакций сохранять обе. Версия протокола, дата выпуска RFC и статус документа — разные поля. Результат D показать отдельно. Если такой набор вопросов слишком мал, оставить D дополнительным опытом.
6. **Общий генератор и отказы.** Использовать одну версию `qwen3:4b-instruct-2507-q4_K_M` через Ollama. На короткий список пронумерованных фрагментов получать русский ответ, утверждения, ID предложений и статус. Приложение разрешает только ID из переданного контекста и извлекает цитаты само. При неполном обосновании обязательной части — отказ с пояснением. При явном расхождении — привести обе нормы, указать даты и границы применимости. Семантическую поддержку оценить вручную. [Сборка Qwen](https://ollama.com/library/qwen3:4b-instruct-2507-q4_K_M)

Фиксируем одинаковые чанки, промпт, версию модели, число кандидатов после каждого поиска и слияния, одинаковый предел контекста. Плановые значения — по 20 кандидатов от каждого используемого поисковика, после слияния до 20, затем top-5 для ответа с единым бюджетом токенов. Записываем, какие фрагменты действительно увидел генератор. Сам перевод добавляет вызов модели, поэтому его время на новом запросе учитывается отдельно от повторного запуска из кеша.

## Как оценивать

**Набор.** До просмотра результатов на финальном тесте зафиксировать 20 русских вопросов, например 4 прямых, 6 на сравнение версий и изменение требований, 6 требующих объединить источники и 4 с недостаточными данными. У каждого один основной тип для подсчёта и дополнительные теги при пересечениях. Для каждого положительного примера разметить минимальные утверждения ответа, точные диапазоны и альтернативные доказательства. Проверять те же факты в последующих поправках и приложениях. Если поздний RFC один покрывает весь ответ, засчитать его и перенести вопрос из группы, требующей двух источников. Для отказов просмотреть ближайшие по смыслу места во всех документах и записать, каких сведений недостаёт. Исключить перефразы пяти пробных вопросов.

**Поиск.** Основная метрика — макроусреднённый Evidence Recall@5 по отвечаемым вопросам. Для каждого допустимого набора считать долю полностью покрытых эталонных утверждений, взять максимум по наборам. Утверждение покрыто, когда среди выбранных фрагментов есть весь минимальный размеченный текст доказательства, с учётом сохранённых интервалов и нормализации пробелов. Перекрывающиеся чанки не дают двойного зачёта. Отдельно подсчитать вопросы, где найден полный допустимый набор. Зафиксировать правило сопоставления до прогона.

**Ответ.** Для каждого существенного утверждения вручную отметить «подтверждено приведённой цитатой», «противоречит ей» или «опоры недостаточно». Частота недоказанных утверждений — сумма двух последних категорий, делённая на число проверенных утверждений в содержательных ответах. Качество обоснования оценить также на уровне вопроса — ответ содержит все обязательные части и для каждой есть подходящая цитата. Показать корректные отказы среди неотвечаемых, ошибочные отказы среди отвечаемых и долю содержательных ответов. Пустой ответ не улучшает метрику поддержки. Рядом с процентами вывести числители и знаменатели.

**Диагностика.** Для ошибок повторить запрос с эталонными фрагментами вместо найденных. Если ответ исправился, проверить ранги и фактически переданный контекст. Если ошибка сохранилась, проверить формулировку вопроса, эталон, промпт и привязку цитат. Сохранять по вопросу конфигурацию, top-K, контекст, ответ и ручную оценку. На 20 вопросах сообщать, какие именно случаи выиграны или потеряны.

## Сокращённый маршрут

**За пять дней** я бы объединил подготовку данных и проверку Mac в первый день, завершил разметку и A во второй, реализовал B/C и запустил сравнение в третий. Четвёртый день целиком отдал бы ручной оценке и диагностике, пятый — чистому запуску, отчёту и защите. Условие этого графика — около 5–6 часов в день и работоспособная Qwen после первого дня.

**За четыре полных дня** защищаемый результат возможен при 6–7 часах в день, знакомом окружении и готовой разметке ко второму вечеру. Для этого оставить A и B как обязательную пару, C включить только при готовом переводчике и времени на проверку дополнительных 20 ответов. Даже если B проиграет A, сравнение остаётся содержательным. Отложить D, reranker, граф документов, интерфейс и отдельную модель-судью. При срыве сроков сохранить время на проверку цитат, реальных ошибок и воспроизводимости. При доступных 2 часах в день расчётная трудоёмкость превышает неделю.

## Проверка плана перед сдачей

- **На вопрос легко ответить из памяти.** Принимать содержательный ответ только с подтверждением приведёнными фрагментами. Время публикации и область действия должны прослеживаться по доказательствам.
- **Отказы маскируют ошибки.** Для каждой конфигурации показать одновременно долю недоказанных утверждений, полноту ответов и ошибочные отказы. Если знаменатель нулевой, показывать «нет данных».
- **Не нашлось трёх показательных ошибок или уверенной ошибки.** Сначала проверить трассы всех конфигураций, включая baseline. Если их мало, подготовить явно обозначенный дополнительный набор сложных вопросов об исключениях и похожих полях. Сохранить фактический ответ и контекст. В таблицу основных 20 дополнительные вопросы не включать. Категоричный ответ на вопрос считать проявлением уверенности в смысле демонстрации, без приписывания вероятности модели.
- **На Mac медленно.** Считать индекс один раз, группировать поколения ответов после поиска, кешировать переводы и сохранять завершённые вызовы. После первого замера экстраполировать машинное время на число запросов. Если 4B не помещается даже с коротким контекстом, испытать меньшую локальную модель на dev и зафиксировать один генератор для всех основных прогонов.
- **Воспроизводимость.** В README дать команды для подготовки данных, индекса, одного вопроса и всей оценки. Сохранить версии зависимостей, ревизию E5, digest Qwen, параметры декодирования, промпт, конфиги и SHA-256 корпуса. После загрузки моделей проверить локальный запуск без внешнего API. Для защиты держать сохранённый вывод реального прогона рядом с живой демонстрацией.
